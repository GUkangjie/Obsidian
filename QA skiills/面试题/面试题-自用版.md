# 一、基础 & 环境类问题
## 什么是 JDK？JDK、JRE、JVM 的关系是什么？
JDK 是 Java 的开发工具包，里面包含了 JRE 和 JVM
- **JVM** 是 Java 虚拟机，负责真正执行 Java 程序 
- **JRE** 是 Java 运行环境，包含 JVM 和运行所需的类库 
- **JDK** 是给开发和测试用的，包含 JRE 以及编译、调试等工具
## 如何配置 Java 环境变量？JAVA_HOME、CLASSPATH、Path 的作用？
JAVA_HOME 指向 JDK 安装路径，Path 是为了能在任意目录执行 Java 命令，CLASSPATH 用来指定类加载路径

# 二、Bug 管理 & 缺陷相关问题
## 什么是 Bug？Bug 的定义是什么？
Bug 是指系统实际表现与需求、设计或用户预期不一致的问题【预期和实际不符】
## 软件缺陷/bug产生的原因有哪些？
- 需求不明确
- 开发代码错误
- 历史设计不全或遗漏
- 边界和异常场景考虑不充分
## Bug 按严重级别如何划分？
致命、严重、一般、轻微
<font color="#ff0000">致命/严重</font>：功能不可用、系统崩溃、数据错误
**一般**：核心功能异常但有替代方案
**轻微**：展示问题、提示问题、体验问题
## Bug 按优先级如何划分？
**高、中、低**
高：本次必须修复完上线
中：不影响核心流程，尽量本次上线
低：对功能影响较小，可以作为优化项后续再上线
## 严重级别和优先级的区别是什么？
Bug 严重等级是用来区分问题本身的影响程度，  
优先级是用来区分修复的先后顺序。  
**一般情况下，严重等级高的 Bug 优先级也会相对较高，但实际还会结合版本节点和业务影响来综合判断，比如一些极端或低频场景的问题会具体问题具体分析。**
## Bug 的完整处理流程是怎样的？/发现bug你们是怎么处理的？
一般发现问题我会先进行复现，确认它是一个bug再提单，然后把对应的开发、产品、测试添加到负责人内，然后填写相关信息包括问题的截图、bug的描述以及bug的严重等级、优先级、发现阶段、是否线上问题等等，最后会发到群内@对应的开发进行修复，开发修复完成后会在测试环境进行复测，复测通过后，还会在上线过程中留意是否确实修复了，最后review完才算真正闭环，关闭bug单。
## 测试人员如何提交一个 Bug？
**平台、方法 、角色**
发现bug我们是使用百度内部的icafe卡片去提交的，一般会提交bug标题、问题截图、复现步骤以及bug的严重等级、优先级、bug分类、发现的角色、是否线上问题等等，最后也会把对应的负责人加到bug里面，然后在需求群同步问题，确保问题被及时跟进和处理。
## Bug 单里通常需要包含哪些内容？
bug标题、问题截图、复现步骤以及bug的严重等级、优先级、bug分类、发现的角色、是否线上问题以及对应的负责角色。
## 什么情况下需要关闭 Bug？什么情况下需要重新打开bug？
一、
- 复测通过后、上线回归无误后
- 沟通确认非bug
- 重复 Bug，已关联处理
二、
- 复测后问题仍然存在
- 修复后引入了新问题
## 如果开发认为“这不是 Bug”，你该怎么处理？
一般来说在case评审时就已经对齐过预期，是否为是Bug 主要看实际表现是否和用例预期一致。如果不一致，会先和开发沟通确认；如果沟通仍有分歧，会对照需求文档，如果需求文档不明确，会找产品确认，三方对齐后最终以产品确认的预期为准。
## 如何保证 Bug 可以稳定复现？
- 明确bug产生的前置条件
- 记录特定的测试数据
- 在保证问题能复现的前提下，简化复现步骤，保证复现步骤稳定
- 多次验证复现结果确保可以稳定复现
## 无法重现的 Bug 应该如何处理？
对于无法重现的 Bug，通常会先补充关键信息，比如发生时间、环境、账号、日志等，并尝试在相同条件下多次验证。如果仍然无法复现，会在 Bug 单中说明当前无法复现的状态，标记为偶现或暂时无法重现，并进行跟踪记录；后续如果再次复现或线上出现相同问题，会重新打开 Bug 继续跟进 
## 如何高质量地记录一个 Bug？ 
开发根据bug的标题和步骤就能很清楚的知道问题所在和如何复现。
信息清晰、可复现。通过 Bug 标题、完整的复现步骤，和问题截图或日志，让开发能够快速理解问题现象并按照步骤稳定复现
## 什么是返测/复测?
开发修复bug后提交验证 ，测试再次进行测试确保问题被修复
##  什么是回归测试？
返测主要是针对单个 Bug 的修复结果进行验证，确认问题是否解决；回归测试则是针对相关功能或已有功能进行重新测试，确保本次修改没有影响其他模块。## 两者的区别是什么？ 
一个是bug的重复验证，一个是测试用例的全部回归
返测关注单个 Bug 是否修复成功，而回归测试关注整体功能的稳定性
# 三、测试相关知识
## 什么是软件测试
**软件测试**是通过人工或自动化的方式，对软件系统进行验证和评估的过程，目的是**发现软件中的缺陷，验证软件是否满足需求和质量标准**
简单来说，就是通过各种方法来看软件到底有没有问题
## 软件测试的根本目的是什么？
软件测试的根本目的是在上线之前尽可能多的发现问题，保障软件质量，提升用户体验
## 软件测试一般包括哪些工作内容？
我主要负责服务端测试工作，一般一个需求从开始，测试需要参加需求评审，补充开发或产品可能会遗漏的点或者提出一些可能存在的问题，开完会要找开发确认排期、开发时间、提测时间以及对应的需求文档；然后会参加技术评审，了解技术逻辑、补充产品业务逻辑，开发给出服务端接口文档后就会介入测试用例的设计，然后在提测前组织case评审，约产品、开发对齐，最后会执行case，一般是测试环境要过两轮，期间如果有bug就提交bug，开发修改完成后复测，确保没有问题，然后上预发布、预发布回归没问题再上线，上线完成还会再次回归。服务端上线完成、客户端也回归无误才会发起上线提审，配合服务端测试过集成，最终产品成功上线
## 测试大纲是什么？ 
我个人理解测试大纲更像是测试前的准备和整体思考。我们团队实际工作中不会单独写测试大纲文档，但在一些需要紧急上线的需求里，会提前列测试点和测试思路，明确测试重点和风险，我觉得这种和测试大纲是比较相似的
## 测试用例是什么？
测试用例是对某一测试场景的具体操作和预期结果描述，用于指导测试执行。**一个好的测试用例，应该是其他测试或者开发在不了解背景的情况下，也能看懂并按步骤复现测试结果。**
## 测试用例一般包含哪些字段？
测试编号、测试标题、前置条件、操作步骤、预期结果、实际结果、测试状态
## 测试报告和测试总结有什么区别？
**测试报告**是告诉大家这个版本目前“是什么状态”，是否具备上线条件，比如测试覆盖情况、发现的 bug 数量、关键用例通过情况、遗留问题以及整体上线风险等。

**测试总结**是测试站在事后视角，对本次需求或版本进行复盘，更多关注测试过程本身，比如测试效率、测试方法是否合适、开发提测质量以及后续可以优化的点。
## 软件测试人员需要具备哪些素质？
- **丰富的测试经验积累**-----badcase或者一些比较经典的业务场景
- **严谨求实的态度**-----不放过丝毫可能存在的问题
- **良好的沟通能力**---和开发、产品能够流畅的沟通、对其需求
- **问题定位能力**---发现问题、定位问题的能力
- **敏捷的思维**----测试用例覆盖率、效率
- **一定的脚本开发能力**----提效
## 测试过程中为什么要保持“怀疑态度”？
<u>测试过程中保持怀疑态度是因为系统本身是不断变化的，  
如果对一些看起来“应该没问题”的地方抱有侥幸心理不去验证，  
或者在 bug 修复后没有对相关功能做回归，很容易引入新的问题。  
所以测试需要对修改保持敏感，带着怀疑去验证每一次改动，  
用比较严谨、求实的态度尽量覆盖可能出现的风险。</u>
# 四、软件生命周期 & 流程
## 软件项目的整体流程是怎样的？
一般是产品提需求，然后写需求文档，开需求评审，开发组织技术评审、给出技术文档、接口文档介入开发，测试写测试用例、组织case评审，执行测试，还有bug的提交跟进修复、测试通过后会上预发布、预发布没问题就上线、上线也会做回归然后走上线提审流程
## 产品、开发、测试在项目中各自承担什么角色？
-产品主要负责确定做什么功能，以及这个功能的目标和取舍， 
-开发负责把需求落地，实现功能本身
-测试更多是站在使用和风险的角度，去验证实现是不是符合预期，有没有遗漏、边界问题，有问题的话会及时反馈并推动修改，同时也会关注改动对已有功能的影响。
## 软件测试在项目中通常从哪个阶段开始？
软件测试是贯穿需求的全流程的
如果有需要具体展开----从需求提出时就开始，直到上线提审
## 软件测试贯穿软件生命周期体现在哪些地方？
从需求评审发现歧义，到开发阶段设计测试点，再到测试阶段执行、上线前把关，以及上线后的问题回溯和总结，其实测试一直都在参与
## 软件测试生命周期包含哪些阶段？
测试准备、测试设计、测试执行、缺陷跟踪、回归验证和总结
## 软件测试的标准流程是什么？
我认为标准的测试流程应该是从一个的需求开始到上线后的回归验证这一整套流程。一般一个需求从开始，测试需要参加需求评审，补充开发或产品可能会遗漏的点或者提出一些可能存在的问题，开完会要找开发确认排期、开发时间、提测时间以及对应的需求文档；然后会参加技术评审，了解技术逻辑、补充产品业务逻辑，开发给出服务端接口文档后就会介入测试用例的设计，然后在提测前组织case评审，约产品、开发对齐，最后会执行case，一般是测试环境要过两轮，期间如果有bug就提交bug，开发修改完成后复测，确保没有问题，然后上预发布、预发布回归没问题再上线，上线完成还会再次回归。服务端上线完成、客户端也回归无误才会发起上线提审，配合服务端测试过集成，最终产品成功上线。

## 测试计划一般包含哪些内容？
我们日常项目里很少写完整的测试计划文档，更多是通过周会的形式，对齐测试排期、风险点和重点内容，避免测试过程中出现问题。我理解测试计划的核心是测试范围、排期和风险控制，我们更多是用会议和对齐的方式来完成这些内容。
## 测试报告一般包含哪些内容？
测试报告应该包含测试范围、测试结论、问题情况、问题解决情况、上线风险以及是否可以上线
## 测试总结一般包含哪些内容？
测试总结更多是事后复盘，比如测试过程中暴露的问题、测试方法是否合理、需求或开发质量的问题，以及后续可以优化的地方。
## 上线前测试主要关注哪些点？
1. 测试用例是否执行回归完成
2. bug是否已修复
3. 上线前的前置工作是否完成[踩过坑：配置项是否配置、建库、脚本等]
4. 核心功能是否实现
# 五、测试模型&开发模型
## 什么是瀑布模型？
瀑布模型是一种传统的软件开发模型，项目按照**需求分析、设计、开发、测试、上线**等阶段顺序推进，每个阶段完成后再进入下一阶段，阶段之间基本不可逆
## 瀑布模型各阶段分别产出哪些文档？
需求阶段——需求文档
开发阶段——技术文档、接口文档
测试阶段——测试用例、测试报告、总结
上线阶段：发布说明、运维文档
## 什么是螺旋模型？
螺旋模型是一种**以风险驱动为核心的迭代开发模型**，将瀑布模型和原型模型结合起来，通过多轮迭代不断识别和降低项目风险
## 螺旋模型每次迭代包含哪些步骤？
- 制定目标和计划  
- 识别并评估风险
- 开发和验证（设计 / 开发 / 测试）    
- 评审结果并决定是否进入下一轮迭代
## 什么是 V 模型？什么是 W 模型？
V 模型是在瀑布模型基础上演变而来的模型，强调**开发阶段和测试阶段一一对应**，测试活动不是只在开发完成后才进行。
W 模型是在 V 模型基础上进一步发展的模型，强调**测试应从需求阶段就开始介入**，在每个开发阶段都有对应的测试活动。
## V 模型和 W 模型的区别是什么？
- V 模型中，测试活动主要在开发完成后集中执行
- W 模型中，测试从需求阶段就开始，全流程参与
## 不同测试阶段之间的区别是什么？
- **单元测试**：由开发完成，测试单个函数或模块，关注代码逻辑是否正确
    
- **集成测试**：测试模块之间、服务之间的接口和数据交互是否正常
    
- **系统测试**：从整体业务角度测试系统功能、流程和异常场景
    
- **验收测试**：从用户或产品角度，验证系统是否满足需求，决定是否可以上线

# 六、测试类型 & 测试方法
## 什么是单元测试？
单元测试一般由开发完成，针对单个函数或模块进行测试，关注代码逻辑是否正确。在之前的团队，测试也会参与单测设计或协助补充关键逻辑的单测用例
## 什么是集成测试（联调测试）？
集成测试是将多个模块或系统进行集成后进行测试，比如服务端与客户端的联调，主要关注接口调用、数据传递以及整体功能是否正常。
## 什么是系统测试？
从整体业务角度测试系统功能、流程和异常场景
## 什么是验收测试（UAT）？
验收测试通常由产品或业务方主导，从用户或业务角度验证功能是否满足需求，决定是否可以上线。
## α 测试和 β 测试有什么区别？
α 测试通常在公司内部进行，由测试人员或内部用户参与，在产品正式对外发布前，验证核心功能和主要问题
β 测试是在产品接近稳定后，向部分真实用户开放，收集真实使用场景下的问题和反馈
## 什么是冒烟测试？
冒烟测试是对系统核心功能和主流程的快速验证，确保系统基本可用，防止明显阻断性问题进入后续测试
## 什么是黑盒测试？
我理解是功能测试，不关注代码逻辑如何实现，从业务逻辑角度去设计测试用例，主要保障产品的功能实现正常
## 什么是白盒测试？
**白盒测试**是指**基于代码内部结构和逻辑**进行的测试方法，通过了解程序的实现方式，设计测试用例来覆盖代码中的**关键分支、判断逻辑、异常处理和边界情况**，从而验证代码实现是否正确。
## 什么是灰盒测试？
灰盒测试介于黑盒和白盒之间，测试人员了解部分系统结构，比如通过抓包、看接口、查日志来定位问题，但不直接修改代码。
## 黑盒测试和白盒测试的区别是什么？
一个是功能测试，一个是对代码进行测试，完全是两种测试方法
## 常见的白盒测试方法有哪些？
- 语句覆盖  
- 分支覆盖 
- 条件覆盖
- 路径覆盖
## 什么是静态测试？什么是动态测试？
静态测试：不运行代码，对需求文档、设计文档或代码进行评审和检查，比如需求评审、代码 review。
动态测试：通过运行系统或程序进行测试，验证功能和逻辑是否正确，是测试工作的主要形式。
## 什么是随机测试？
随机测试是在没有严格测试路径限制的情况下，模拟用户随机操作系统，用于发现用例未覆盖的问题，常作为补充测试手段。
## 手工测试和自动化测试的区别是什么？
手工测试更灵活，适合探索性测试和复杂业务场景；  
自动化测试适合回归测试和高频场景，可以提高测试效率、降低重复劳动成本。
## 接口测试主要测试哪些内容？
1. 接口功能是否正确
2. 入参、出参及数据格式
3. 边界值和异常场景
4. 业务逻辑是否符合预期
5. 接口幂等性、频率限制、安全性等

# 七、测试策略 & 原则
## 常见的软件测试策略有哪些？
常见的软件测试策略包括：
- **功能测试**：验证功能是否按需求实现
- **回归测试**：验证修改是否影响已有功能
- **冒烟测试**：验证核心功能是否可用
- **异常与边界测试**：验证异常输入和边界场景 
- **风险驱动测试**：优先测试高风险、高影响模块
- **自动化测试**：通过脚本提升测试效率
## 软件测试的基本原则有哪些？
1. 测试应尽早介入，并贯穿软件的整个生命周期；
2. 测试应基于需求开展，保证需求的可追溯性；
3. 测试应尽量由相对独立于开发的角色执行，保证客观性；
4. 穷尽测试是不可能的，应基于风险和优先级合理取舍；
5. 对测试结果要进行有效分析，而不是只关注执行过程；
6. 缺陷通常存在集群现象，应重点关注高风险模块。
## 什么是缺陷的「二八定律」？
在软件系统中，大约 **80% 的缺陷集中在 20% 的模块**中，因此测试时应重点关注高复杂度、高改动频率的模块
## 什么是响应时间的 2-5-10 原则？
- **2 秒以内**：用户感觉流畅
- **5 秒左右**：用户可以接受
- **10 秒以上**：用户明显感到卡顿，可能放弃操作
## 测试中为什么不能过度测试？
测试资源是有限的，过度测试会导致时间和人力浪费，同时可能影响项目交付效率。测试应基于需求、风险和优先级进行，而不是追求所有场景都覆盖。
## 什么是 Bug 的「集群现象」？
Bug 的集群现象指的是：缺陷往往集中出现在某些模块或功能区域，而不是均匀分布在系统中。通常是逻辑复杂、改动频繁或历史问题较多的模块。

## C/S 架构和 B/S 架构的区别是什么？  
**C/S**需要安装客户端，客户端需要单独升级；对操作系统依赖较强，跨平台性相对较弱，整体维护成本较高。
**B/S**通过浏览器访问，主要在服务端进行升级；对客户端要求低，跨平台性强，维护成本相对较低
## 为什么 B/S 架构更容易维护？   
- 无需客户端安装和升级
- 升级集中在服务端
- 跨平台成本低
## 测试环境需要满足哪些基本要求？
**环境相对稳定**
不频繁重启、不随意改配置
**版本可控、可回滚**
能明确当前测试的代码版本
**数据可构造、可清理**
支持造数据、删数据、重置数据
**与线上保持一定一致性**
接口、依赖、配置尽量接近线上
**具备必要的日志和监控能力**
方便问题定位
## 九、特殊场景面试题
## 如果没有需求文档，你会如何测试？
如果没有正式需求文档，我会先通过和产品、开发沟通，明确核心功能和改动点；同时结合历史版本行为、接口文档或代码逻辑，梳理测试点，重点覆盖主流程、异常场景和改动影响范围，确保核心功能不出问题
## 如果测试时间不够，你会如何安排测试？
如果需求比较复杂、测试时间不足，我会第一时间同步测试进度和风险，根据影响范围和改动点进行风险评估，优先保证核心功能和主流程的测试；  
同时视情况协调其他测试同学协助，或者和产品、开发沟通是否需要延期提测，确保在可控风险范围内上线。
## 上线前发现 Bug 该怎么办？
如果上线前发现 Bug，会根据 Bug 严重程度评估是否影响核心功能：
- 严重 Bug：必须阻断上线，推动修复并回归
- 一般 Bug：评估是否可以延期修复，明确上线风险并同步相关方  
测试会给出是否支持上线的结论，但最终由产品决策
## 上线后发现 Bug 该怎么办？
上线后发现 Bug，会第一时间确认影响范围和严重程度，  
若影响用户或核心功能，会推动紧急修复或回滚；  
同时复盘问题原因，补充测试用例，避免类似问题再次发生

## 测试过程中发现严重 Bug，你会如何推动解决？
对于严重 Bug，我会第一时间同步开发和相关负责人，  
明确问题影响范围和风险等级，协助开发快速定位问题；  
在修复后重点回归相关功能，确保问题彻底解决。
## 如何保证版本质量？
流程规范是保障质量的重要基础，在快速迭代的项目中，测试需要从需求阶段就全流程介入。我们会参与需求和技术评审，提前识别风险点；在开发阶段基于接口和技术方案设计测试用例；提测后重点进行多轮回归、问题跟踪和风险确认，确保预发布和线上版本稳定。通过在每个关键环节介入，来保证整体版本质量。
## 系统上线的标准是什么？
上线的核心标准是：功能完整、核心问题清零、风险可控，并且经过测试和验收确
认可以上线

## 什么是 URL？URL 的组成结构是什么？
URL：统一资源定位符，用于定位互联网上的资源。
组成结构：
**协议://主机名:端口号/路径?参数#锚点**
## HTTP 和 HTTPS 的默认端口分别是什么？
**HTTP**——80
**HTTPS**——443
## 什么是主键？为什么主键不能重复？
**主键（Primary Key）**：用于唯一标识一条记录的字段或字段组合。
不能重复的原因：
- 用来唯一定位数据
- 保证数据完整性
- 便于索引和关联查询
## 什么是外键？
外键：用于建立表与表之间关系的字段，通常指向另一张表的主键。
- 保证数据一致性
- 防止产生无效数据
## 常用的 SQL 查询关键字有哪些？
常见的有：
**select、from、where、group by、having、order by、limit**
联表相关：
**join、inner join、left join、right join**
## where、group by、having、order by 的执行顺序是什么？
**from → where → group by → having → select → order by**
先过滤、再分组、后排序
## count、sum、avg、max、min 的作用是什么？
- **count**：统计行数
- **sum**：求和 
- **avg**：平均值
- **max**：最大值
- **min**：最小值
## inner join 的作用是什么？
返回两张表中**关联字段匹配的记录**，不匹配的不会返回。
## truncate、delete、drop 的区别是什么？
|操作|作用|是否可回滚|是否清表结构|
|---|---|---|---|
|delete|删除数据|可以|否|
|truncate|清空表数据|不可以|否|
|drop|删除表|不可以|是|
## 如何查询分组后的统计结果？
使用 **group by + 聚合函数**
## 如何进行多表联查？
使用 **join**
## 为什么修改数据后需要 commit？
因为数据库默认使用事务，**commit 用于提交事务，使数据永久生效**。
如果不 commit，数据可能被回滚，其他事务不可见
