# 一、基础 & 环境类问题
## 什么是 JDK？JDK、JRE、JVM 的关系是什么？
JDK 是 Java 的开发工具包，里面包含了 JRE 和 JVM
- **JVM** 是 Java 虚拟机，负责真正执行 Java 程序 
- **JRE** 是 Java 运行环境，包含 JVM 和运行所需的类库 
- **JDK** 是给开发和测试用的，包含 JRE 以及编译、调试等工具
## 如何配置 Java 环境变量？JAVA_HOME、CLASSPATH、Path 的作用？
JAVA_HOME 指向 JDK 安装路径，Path 是为了能在任意目录执行 Java 命令，CLASSPATH 用来指定类加载路径

# 二、Bug 管理 & 缺陷相关问题
## 什么是 Bug？Bug 的定义是什么？
Bug 是指系统实际表现与需求、设计或用户预期不一致的问题【预期和实际不符】
## 软件缺陷/bug产生的原因有哪些？
- 需求不明确
- 开发代码错误
- 历史设计不全或遗漏
- 边界和异常场景考虑不充分
## Bug 按严重级别如何划分？
致命、严重、一般、轻微
<font color="#ff0000">致命/严重</font>：功能不可用、系统崩溃、数据错误
**一般**：核心功能异常但有替代方案
**轻微**：展示问题、提示问题、体验问题
## Bug 按优先级如何划分？
**高、中、低**
高：本次必须修复完上线
中：不影响核心流程，尽量本次上线
低：对功能影响较小，可以作为优化项后续再上线
## 严重级别和优先级的区别是什么？
Bug 严重等级是用来区分问题本身的影响程度，  
优先级是用来区分修复的先后顺序。  
**一般情况下，严重等级高的 Bug 优先级也会相对较高，但实际还会结合版本节点和业务影响来综合判断，比如一些极端或低频场景的问题会具体问题具体分析。**
## Bug 的完整处理流程是怎样的？/发现bug你们是怎么处理的？
一般发现问题我会先进行复现，确认它是一个bug再提单，然后把对应的开发、产品、测试添加到负责人内，然后填写相关信息包括问题的截图、bug的描述以及bug的严重等级、优先级、发现阶段、是否线上问题等等，最后会发到群内@对应的开发进行修复，开发修复完成后会在测试环境进行复测，复测通过后，还会在上线过程中留意是否确实修复了，最后review完才算真正闭环，关闭bug单。
## 测试人员如何提交一个 Bug？
**平台、方法 、角色**
发现bug我们是使用百度内部的icafe卡片去提交的，一般会提交bug标题、问题截图、复现步骤以及bug的严重等级、优先级、bug分类、发现的角色、是否线上问题等等，最后也会把对应的负责人加到bug里面，然后在需求群同步问题，确保问题被及时跟进和处理。
## Bug 单里通常需要包含哪些内容？
bug标题、问题截图、复现步骤以及bug的严重等级、优先级、bug分类、发现的角色、是否线上问题以及对应的负责角色。
## 什么情况下需要关闭 Bug？什么情况下需要重新打开bug？
一、
- 复测通过后、上线回归无误后
- 沟通确认非bug
- 重复 Bug，已关联处理
二、
- 复测后问题仍然存在
- 修复后引入了新问题
## 如果开发认为“这不是 Bug”，你该怎么处理？
一般来说在case评审时就已经对齐过预期，是否为是Bug 主要看实际表现是否和用例预期一致。如果不一致，会先和开发沟通确认；如果沟通仍有分歧，会对照需求文档，如果需求文档不明确，会找产品确认，三方对齐后最终以产品确认的预期为准。
## 如何保证 Bug 可以稳定复现？
- 明确bug产生的前置条件
- 记录特定的测试数据
- 在保证问题能复现的前提下，简化复现步骤，保证复现步骤稳定
- 多次验证复现结果确保可以稳定复现
## 无法重现的 Bug 应该如何处理？
对于无法重现的 Bug，通常会先补充关键信息，比如发生时间、环境、账号、日志等，并尝试在相同条件下多次验证。如果仍然无法复现，会在 Bug 单中说明当前无法复现的状态，标记为偶现或暂时无法重现，并进行跟踪记录；后续如果再次复现或线上出现相同问题，会重新打开 Bug 继续跟进 
## 如何高质量地记录一个 Bug？ 
开发根据bug的标题和步骤就能很清楚的知道问题所在和如何复现。
信息清晰、可复现。通过 Bug 标题、完整的复现步骤，和问题截图或日志，让开发能够快速理解问题现象并按照步骤稳定复现
## 什么是返测/复测?
开发修复bug后提交验证 ，测试再次进行测试确保问题被修复
##  什么是回归测试？
返测主要是针对单个 Bug 的修复结果进行验证，确认问题是否解决；回归测试则是针对相关功能或已有功能进行重新测试，确保本次修改没有影响其他模块。## 两者的区别是什么？ 
一个是bug的重复验证，一个是测试用例的全部回归
返测关注单个 Bug 是否修复成功，而回归测试关注整体功能的稳定性
# 三、测试相关知识
## 什么是软件测试
**软件测试**是通过人工或自动化的方式，对软件系统进行验证和评估的过程，目的是**发现软件中的缺陷，验证软件是否满足需求和质量标准**
简单来说，就是通过各种方法来看软件到底有没有问题
## 软件测试的根本目的是什么？
软件测试的根本目的是在上线之前尽可能多的发现问题，保障软件质量，提升用户体验
## 软件测试一般包括哪些工作内容？
我主要负责服务端测试工作，一般一个需求从开始，测试需要参加需求评审，补充开发或产品可能会遗漏的点或者提出一些可能存在的问题，开完会要找开发确认排期、开发时间、提测时间以及对应的需求文档；然后会参加技术评审，了解技术逻辑、补充产品业务逻辑，开发给出服务端接口文档后就会介入测试用例的设计，然后在提测前组织case评审，约产品、开发对齐，最后会执行case，一般是测试环境要过两轮，期间如果有bug就提交bug，开发修改完成后复测，确保没有问题，然后上预发布、预发布回归没问题再上线，上线完成还会再次回归。服务端上线完成、客户端也回归无误才会发起上线提审，配合服务端测试过集成，最终产品成功上线
## 测试大纲是什么？ 
我个人理解测试大纲更像是测试前的准备和整体思考。我们团队实际工作中不会单独写测试大纲文档，但在一些需要紧急上线的需求里，会提前列测试点和测试思路，明确测试重点和风险，我觉得这种和测试大纲是比较相似的
## 测试用例是什么？
测试用例是对某一测试场景的具体操作和预期结果描述，用于指导测试执行。**一个好的测试用例，应该是其他测试或者开发在不了解背景的情况下，也能看懂并按步骤复现测试结果。**
## 测试用例一般包含哪些字段？
测试编号、测试标题、前置条件、操作步骤、预期结果、实际结果、测试状态
## 测试报告和测试总结有什么区别？
**测试报告**是告诉大家这个版本目前“是什么状态”，是否具备上线条件，比如测试覆盖情况、发现的 bug 数量、关键用例通过情况、遗留问题以及整体上线风险等。

**测试总结**是测试站在事后视角，对本次需求或版本进行复盘，更多关注测试过程本身，比如测试效率、测试方法是否合适、开发提测质量以及后续可以优化的点。
## 软件测试人员需要具备哪些素质？
- **丰富的测试经验积累**-----badcase或者一些比较经典的业务场景
- **严谨求实的态度**-----不放过丝毫可能存在的问题
- **良好的沟通能力**---和开发、产品能够流畅的沟通、对其需求
- **问题定位能力**---发现问题、定位问题的能力
- **敏捷的思维**----测试用例覆盖率、效率
- **一定的脚本开发能力**----提效
## 测试过程中为什么要保持“怀疑态度”？
<u>测试过程中保持怀疑态度是因为系统本身是不断变化的，  
如果对一些看起来“应该没问题”的地方抱有侥幸心理不去验证，  
或者在 bug 修复后没有对相关功能做回归，很容易引入新的问题。  
所以测试需要对修改保持敏感，带着怀疑去验证每一次改动，  
用比较严谨、求实的态度尽量覆盖可能出现的风险。</u>
# 四、软件生命周期 & 流程
## 软件项目的整体流程是怎样的？
一般是产品提需求，然后写需求文档，开需求评审，开发组织技术评审、给出技术文档、接口文档介入开发，测试写测试用例、组织case评审，执行测试，还有bug的提交跟进修复、测试通过后会上预发布、预发布没问题就上线、上线也会做回归然后走上线提审流程
## 产品、开发、测试在项目中各自承担什么角色？
-产品主要负责确定做什么功能，以及这个功能的目标和取舍， 
-开发负责把需求落地，实现功能本身
-测试更多是站在使用和风险的角度，去验证实现是不是符合预期，有没有遗漏、边界问题，有问题的话会及时反馈并推动修改，同时也会关注改动对已有功能的影响。
## 软件测试在项目中通常从哪个阶段开始？
软件测试是贯穿需求的全流程的
